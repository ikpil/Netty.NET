검토일: 2026-10-02. 이 문서는 목표 설정을 위한 제안이다.

## 확인한 근거

- 원본 `D:\workspace\netty`의 HEAD와 README 기준은 모두
  `e66ce34777f9c4a0c57ac74bb97396ca2f54b43c`이다.
- 현재 목표에는 이미 CLR 설계 검토, Task/TCS, 표준 컬렉션, 원본 주석,
  실제 소비자 확인, 기본 전체 빌드·테스트의 완료 기준이 들어 있다.
- `src/Netty.NET.Common/Concurrent/DefaultPromise.cs`는 결과를 TCS로
  관리하지만, `IFuture.cs`와 `IPromise.cs`에는 Java식 공개 API가 남아 있다.
  내부 구현 대체와 공개 API 이행은 별도의 작업이다.
- `docs/common-task-composition.md`에는 Task.WhenAll 및 TCS를 사용하는
  대체 결정과 취소·예외·생산자 소유권의 의미 차이가 기록되어 있다.
  원본 `PromiseCombiner.java`는 executor 내 접근과 listener 알림을 사용한다.
  Task 집계로 바꾸면 호출부의 상태 접근 위치도 함께 검토해야 한다.
- 이 제안의 초안 검토 시점에는 `AsciiString.cs`의 문자열 변환이
  Encoding.ASCII를 사용했고, 숫자 파싱은 culture를 지정하지 않았다.
  이후 [문자열·메모리 포팅](common-ascii-memory.md)에서 바이트 표현과
  네이티브 생성자를 개선했다. 숫자 파싱 계약의 검토는 계속 필요하다.
- 원본 `AbstractConstant.java`의 공유 static 카운터와 final identity 메서드는
  CLR의 닫힌 제네릭 타입별 static 저장소와 재정의 가능성을 고려해야 한다.
  현재 C# 구현에는 이를 해결하는 비제네릭 시퀀스와 sealed override가 있다.
- 원본 `buffer/.../PoolChunk.java`는 LongLongHashMap의 get/put/remove를
  사용한다. Dictionary로 대체할 때도 누락값 -1과 기존 값 반환 규칙을
  호출부에서 처리해야 한다. 클래스 생략이 호출부 계약의 생략은 아니다.
- 제안 초기에는 기본 Debug/Release 빌드가 성공하지만 전체 테스트에 실패가
  남아 있었다. 이후 native/heap memory 작업으로 기본 전체 테스트는 통과했다.
  필수 stub, 미검토 source와 공개 API 이행은 계속 남아 있다. 선택된 PortingBatch 통과, 전체 빌드 성공,
  전체 테스트 통과와 기능 설계 검토 완료는 각각 다른 증거다.

## 첫 초안

> 고정된 Netty 4.2 원본을 근거로 common과 테스트를 C#에 맞게 포팅한다.
> Future/Promise는 Task/TCS를, 컬렉션은 .NET 표준 컬렉션을 우선 사용한다.
> Java와 CLR의 언어·실행·메모리 차이를 검토하고, 필요한 Netty 동작과
> 원본 주석을 보존한다. 전체 테스트가 통과할 때까지 작업한다.

## 초안 비평과 개선

1. **'필요한 동작'의 범위가 불명확하다.**
   C# 관례를 이유로 알림 위치, 실행 순서, 자원 소유권까지 바꿀 수 있다.
   보존할 기능 계약, 변경 가능한 API 표현, 제외 가능한 JVM 구조를 구분한다.
2. **타입 치환을 설계 완료로 오해할 수 있다.**
   Task는 결과 관찰 수단이다. executor의 직렬 실행이나 종료 정책까지
   대체한다는 뜻은 아니다. 컬렉션도 사용처의 복합 연산을 함께 검토한다.
3. **현재 코드와 원본 사용처에 대한 재검토가 부족하다.**
   테스트가 통과한 Java식 API와 중복 상태도 검토 대상으로 명시한다.
   아직 포팅되지 않은 buffer/transport/codec 소비자도 근거로 확인한다.
4. **테스트를 바꿔 의미 차이를 숨길 수 있다.**
   원본 시나리오를 추적하고, 표준 기능으로 달라지는 의미를 별도 기록한다.
   새로운 테스트가 새 구현만 검증하는 것으로 동등성을 주장하지 않는다.
5. **완료와 진행의 구분이 약하다.**
   선택된 batch, 전체 빌드, 기능 검토, 주석 보존, 성능 검증을 분리한다.
   Java 파일 수와 C# 파일 수가 같아야 한다는 잘못된 지표를 배제한다.
6. **단계 순서와 작업 산출물이 없다.**
   의존 관계와 계약을 먼저 정리하고, 작은 기능 단위로 구현한다.
   기능별 결정 기록과 C# 소비자 검증을 요구하되 문서 작성만 반복하지 않는다.

## 상세 프롬프트의 재비평

검토 항목이 많아져도 판단 우선순위가 없으면 결정은 흔들릴 수 있다.
필요한 Netty 계약을 먼저 확정하고, 이를 충족하는 표준 .NET 기능을 고르며,
부족한 정책만 구현한다. C# 관례와 기존 Java 구현이 충돌하면 소비자 영향과
검증 가능한 대안을 비교한다. 성능 때문에 전용 구조를 유지한다면 측정 근거를
남기되, 특정 벤치마크 수치나 Java와 동일한 성능을 임의의 완료 조건으로 만들지 않는다.

또한 기존 API에 Task 속성을 추가한 상태를 API 이행 완료라고 해석할 수 있다.
기능별 완료에는 원본 계약뿐 아니라 자연스러운 C# 호출 방식, 실제 호출부의
이행 여부, 남은 어댑터의 필요성을 함께 확인하도록 한다.

주석 보존과 문서 정확성도 구분해야 한다. 원문을 유지하되 대응 구현의 의미가
달라졌다면 CLR 설명을 덧붙인다. 표준 기능으로 대체하여 대응 코드가 사라진
부분은 원본 위치와 주석을 설계 기록에 보존한다. 주석을 넣기 위한 빈 클래스나
가짜 필드를 만들지 않는다.

마지막으로 common의 완료와 Netty.NET 전체의 완료를 분리한다.
향후 buffer/transport/codec에서 사용할 대표 시나리오를 common의 C# 소비자
테스트로 검증하되, 그 모듈 전체를 이번 단계에서 구현할 필요는 없다.
지원 환경은 현재 프로젝트의 선언과 사용자 요구를 기준으로 명시하고,
멀티 타깃, 모든 OS, AOT 등 별도 제품 요구를 추측으로 추가하지 않는다.

1. 포팅의 성공 기준과 판단 우선순위

판단 순서는 필요한 Netty 계약 확정 → 이를 충족하는 .NET 표준 기능 선택 →
부족한 정책 구현 → C# 공개 API와 호출부 검증이다.

원본의 기능, 프로토콜 관련 결과, 상태 전이, 실행 순서,
executor 소유 상태의 접근 규칙, 자원 소유권 및 실패 조건을 먼저 이해한다.
이후 그 계약을 충족하는 C# API와 CLR 구현을 선택한다.

Java 클래스·파일 수, 상속 구조, 이름, JDK API와의 문법 호환을
재현하는 것은 성공 기준이 아니다. 테스트 호출 문법도 API 설계 근거가 아니다.

각 요구를 다음과 같이 구분한다.
- 보존: Netty의 실제 기능과 소비자에게 필요한 동작 계약.
- CLR 적응: Task, 취소 토큰, 예외, 이름 등 C# API의 표현과 표준 관례.
- 대체·제외: 표준 기능으로 충족되는 구조 또는 JVM에만 필요한 장치.

표준 기능이 원본과 다르게 동작한다면 차이가 어느 범주에 속하는지 밝힌다.
C# 관례라는 이유만으로 필요한 Netty 계약을 변경하지 않는다.
소비자에 영향이 없거나 호출부 적응으로 해결되는 차이는 근거와 테스트를 남긴다.
필수 계약을 바꾸거나 요구가 충돌하여 판단할 수 없을 때만 사용자에게 질문한다.

2. 근거와 기존 구현 검토

각 기능을 구현하기 전에 고정된 원본 구현, 문서·구현 주석, 테스트,
common 및 다른 원본 모듈의 실제 사용처를 확인한다.
필요한 계약과 .NET 표준 기능의 의미를 공식 문서 또는 실제 구현으로 비교한다.

기존 C# 코드와 통과한 테스트도 같은 기준으로 다시 검토한다.
원본 동작을 의도된 계약, JVM 제약, 구현 세부, 의심되는 결함으로 구분한다.
의심되는 결함을 추측으로 수정하지 말고 재현과 영향 분석을 먼저 한다.

기능별 기록에는 원본 위치, 소비자, 보존할 계약, CLR 선택,
의미 차이와 호출부 영향, 대응 테스트, 남은 문제를 적는다.
표준 기능으로 대체한 항목에는 억지로 C# 대응 클래스를 만들지 않는다.
현재 C# 사용처가 없다는 이유만으로 아직 필요한 기능을 제외하지 않는다.

3. 비동기, 취소와 실행 모델

비동기 결과의 공개 API는 Task/Task<T>를 기본으로 설계한다.
생산자가 완료시키는 외부 작업은 TaskCompletionSource를 우선 검토하고,
소비자에게 완료 권한을 넘기지 않는다. Future/Promise 계층은 전제하지 않는다.

결과 완료와 알림 실행을 구분한다. 필요한 경우에만 executor 알림,
진행 통지, 재진입·순서 정책을 추가한다. Task 위에 같은 결과 상태를
중복 저장하지 않는다. 추가 상태에는 독립된 목적과 일관성 검증이 있어야 한다.

다음을 별도로 설계하고 검증한다.
- 호출 전 거부, queued 상태, 실행 시작과 완료 사이의 경쟁.
- 취소 요청, 작업의 실제 취소 완료, 소비자의 대기 취소.
- 취소 가능 경계, 공유 작업과 취소 토큰의 소유자.
- listener/continuation의 실행 위치, 순서, 동기 실행과 재진입.
- 다중 실패, 취소와 실패의 혼합, 예외 및 취소 토큰 전달.
- timeout, shutdown, disposal과 그 이후의 제출·완료 처리.

Task/Task.Run을 event loop의 동의어로 취급하지 않는다.
직렬 호출, thread affinity, 공정성, 예약 실행, 깨우기와 종료 규칙을 확인한다.
async delegate의 시작 순서와 await를 포함한 전체 작업의 직렬화는 구분한다.
await 이후 executor 소유 상태에 접근하는 방법을 API와 예제로 명확히 한다.
ExecutionContext/SynchronizationContext 흐름과 사용자 코드의 실행 위치를 검토한다.
ValueTask는 사용 제약과 할당·성능 측정이 선택을 뒷받침할 때 적용한다.

4. 컬렉션과 동시성

Dictionary, HashSet, List, ConcurrentDictionary, ConcurrentQueue,
PriorityQueue 및 필요한 경우 Channel 등 표준 기능을 우선 비교한다.

각 사용처에서 참조 동일성·값 동등성, null과 누락값, 기존 값 반환,
순서·우선순위 변경·삭제, 용량·거부·backpressure, 복합 연산의 원자성,
factory 중복 실행, 열거·snapshot, 메모리 공개와 경쟁을 확인한다.

LongLongHashMap을 Dictionary<long,long>으로 충분히 대체할 수 있다면
Java 전용 자료구조를 복제하지 않는다. 대신 누락값과 put/remove의
반환 의미 등 필요한 차이는 소비자에서 처리한다.
표준 컬렉션의 thread-safe 표기만으로 복합 동작의 안전성을 주장하지 않는다.
직접 구현에는 표준 기능이 충족하지 못하는 계약이나 측정 근거를 남긴다.

5. 언어와 런타임 차이

해당 기능과 관련된 차이를 실제 코드와 테스트에 반영한다.
- Java 타입 소거와 CLR 런타임 제네릭, 제네릭 타입별 static 저장소.
- 참조·값 타입, boxing, null/default(T), 분산, 동일성과 타입 제약.
- signed byte, overflow, shift, endian과 시간 단위.
- 문자열 비교와 culture, Unicode, encoding/BOM, 잘못된 입력 처리.
- ThreadLocal/AsyncLocal, 물리 스레드와 논리 실행 문맥, 정리 책임.
- Java interrupt와 협력적 취소, await/동기 대기 및 예외 전달.
- GC/weak reference/finalizer, reflection, native 자원과 지원 OS 차이.

시간 계산에는 단조 시간과 실제 시각을 구분하고,
deadline·overflow·주기 실행·시간 해상도를 검토한다.
Unsafe/JNI/ClassLoader 등은 목적에 맞는 CLR 구현이나 제외 근거를 남긴다.
필수 기능을 no-op, null, 기본값 또는 가짜 성공으로 숨기지 않는다.

6. 메모리와 자원 수명

배열, Span, Memory, pool, native memory에는 소유자와 사용 기간,
복사/view/slice 여부, 반환·해제 책임과 공유 규칙을 명시한다.
async 중 유효 기간, 반환 후 접근, 중복 반환, 동시 해제와 재사용을 검증한다.
GC나 IDisposable만으로 shared pooled buffer의 retain/release를 대체하지 않는다.
ByteBuffer를 Stream으로 치환하는 등 표면적 타입 대응을 피한다.
일반 객체의 GC 수명과 공유 storage의 사용권을 구분한다.

7. 공개 API와 원본 주석

C# 표준 타입, async 패턴, 명명·예외 관례에 맞는 주 공개 API를 정한다.
기존 Java식 API를 변경할 때 영향받는 C# 호출부와 원본 소비자를 함께 확인한다.
호환 어댑터에는 필요한 사용처와 역할을 기록한다.
동일 기능을 제공하는 두 API 체계를 이유 없이 영구 유지하지 않는다.

실제로 포팅한 원본 코드의 라이선스, 문서 주석, 구현 주석을 모두 보존한다.
대응 구현 가까이에 두고, CLR에서 달라진 의미와 실제 사용법을 추가로 설명한다.
원본 주석 보존이 틀린 Java API 설명을 C# 문서로 방치하는 이유가 되어서는 안 된다.
대체·제외 항목은 원본과 결정 이유를 기록하고 무의미한 클래스를 만들지 않는다.
대응 코드가 사라진 부분의 원본 주석은 원본 위치와 함께 설계 기록에 보존한다.
Task 속성이나 새 네이티브 API가 존재한다는 사실만으로 API 이행을 완료 처리하지 않는다.
실제 호출부 이행 여부와 남은 어댑터의 필요성도 확인한다.

8. 테스트, 진행과 완료

원본 테스트의 시나리오와 검증 의미를 추적 가능하게 유지한다.
삭제·대체·skip에는 원본 시나리오, 이유와 대응 검증을 기록한다.
테스트 기대값 변경만으로 동등성을 주장하지 않는다.
경쟁·재진입·취소·소유권에는 CLR 회귀 테스트를 추가한다.
경쟁 테스트는 가능한 한 동기화로 순서를 제어하고 실행 환경의 우연에 의존하지 않는다.
필요하면 고정된 Java 원본을 실행해 비교한다.
C# 소비자 예제로 API 사용, 실행 위치와 자원 수명을 검증한다.
아직 포팅하지 않은 buffer/transport/codec의 대표 사용처도 common의
소비자 테스트로 표현한다. 해당 모듈 전체 구현까지 이번 단계에 포함하지 않는다.

선택된 테스트 실행은 진행 확인이다. 기본 전체 검증을 대신하지 않는다.
임시 PortingBatch 설정은 전체 테스트가 기본으로 빌드된 뒤 제거했다.
부분 실행이 필요하면 dotnet test의 --filter를 사용한다.
주석 수, 테스트 수, 원본 파일 수만으로 기능 완성을 판단하지 않는다.
성능 최적화는 정확성 이후 진행하며 할당량·처리량·지연의 조건과 결과를 제시한다.
기존 Netty와 동급 성능이라고 측정 없이 주장하지 않는다.
동일 성능이나 임의의 벤치마크 수치를 자동으로 완료 조건에 추가하지 않는다.

common 완료 조건:
- 모든 원본 source/test 항목과 관련 의존성의 구현·대체·제외가 근거와 함께 정리됨.
- 필요한 기능의 stub과 미해결 필수 계약·API 이행 문제가 남지 않음.
- 실제 원본 소비자를 만족하는 C# 사용 방식과 대응 검증이 있음.
- 기본 설정의 전체 솔루션 빌드와 테스트가 Debug/Release에서 통과함.
- 제외·skip 각각에 타당한 이유가 있으며 실패를 숨기는 제외가 없음.
- 원본 주석·라이선스가 보존되고 C# 설명, README와 manifest가 구현과 일치함.
- 지원 TFM/OS, 검증 환경과 검증하지 못한 범위가 명확함.

이 조건은 common 단계의 완료를 뜻한다. Netty.NET 전체 완료는 후속 모듈과
프로토콜·통합 검증까지 끝난 별도 단계다. 지원 TFM/OS 확대와 AOT 지원은
확인된 제품 요구가 있을 때 범위를 정한다.

9. 다음 작업 순서

원본·소비자 확인 → 계약과 CLR 선택 기록 → 구현·호출부 이행 →
